## 一、起因与实测数字

外部审阅跑了一轮之后说「提示词 14500 字符太长，需要优化，能压到 5000~7000」。

数字是真的：`trellis/_当前提示词全量样本.md` 里 TRACKER SYSTEM PROMPT 那一块实测 14573 字符。但那只是半张账。

tracker 支流每轮的**固定**开销（2026-09-04 实测，孕晚期单胎、无衣柜、无繁殖心理、日记开）：

| | 字符 | ~token |
|---|---|---|
| system prompt（**真实**默认系统提示词，非样本里那个占位桩） | 16479 | 9796 |
| user 里的 `available_tools` | 13053 | 5684 |
| user 里的 `existing_state` | 718 | 213 |
| **固定小计** | **30250** | **15692** |
| 主流侧注入（另一路，不是问题） | 2482 | 1418 |

两处被漏掉了：

1. **样本文档里 `settings.systemPrompt` 是占位桩**（只有「你是一个状态追踪器。」一句）。换成真实的 `DEFAULT_SYSTEM_PROMPT`（`state.js:90`，约 1550 字符的 JSON 契约＋逐工具路由）后是 16479。
2. **样本文档里没有 `available_tools`。** 但工具定义不走 OpenAI 原生 `tools` 参数——`api.js:1063` 是 `JSON.stringify(payload)` 塞进 user message，跟 system 同一个请求。这一块 13053 字符（本场景可见 19 个工具；24 个全可见时 17783）。

所以真实固定开销约 **3 万字符 / 1.57 万 token**，不是 14500。

主流侧总量才 2482 字符，**「压到 5000~7000」在那一侧根本砍不出来**；审阅意见里「宫缩/漏出/前驱/便意分档该改」指的那几段全在主流侧（`METABOLISM_BAND_NARRATIVE_GUIDE`），而且已经被 `needsBandGuide` 挡过一道。「种族生理该改」那条也是错的：`collectRelevantRaces` 早就只吐在场角色、精液来源、胎儿父源、孩子的种族。

## 三、定位：三层分类与一条铁律

提示词内容按「能不能条件化」分三层，各层安全性完全不同：

| 层 | 内容 | 能否门控 |
|---|---|---|
| **契约层** | 报数入口、JSON 输出结构、`[bsPassedTime 强制规则]`、逐角色检查清单 | **永不条件化。** 掉了＝引擎断粮，且静默 |
| **档位演出词** | 六档/五档/四档各档写法 | 可裁到「当前档±1」，门是数值的纯函数（尿意已这么做） |
| **阶段段落** | 产程/破水/前驱/入盆/产后/children/bio | 可按 `base.stage` 门控 |

**铁律：断言面是组装后的整个请求（system ＋ available_tools），不是 system prompt 单独。** 否则「唯一真源住在工具描述里」这件事就会被漏掉。

**方向性纠正：审阅意见里「正文出现什么才触发哪部分」，在 tracker 这一侧不能这么做。**

tracker 的职责是**判定**事件是否发生。把漏尿的报数说明门控在「正文已经写了漏尿」上是因果倒置——这系统里漏没漏是引擎掷的，不是正文说的（`getUrineStressLeakChance`），而正文由主模型写、主模型读的是另一份提示词。关键词门控只能用在**主流侧的演出词**，且永远不能用在报数契约上。

## 六、第二步：正反双向断言 ＋ 契约恒在断言（纯新增）

沿用已有写法，不发明新的。`tests/race_catalog.test.mjs:32-37` 和 `tests/tracker_pipeline.test.mjs:132-145` 已经是 `assert.ok(includes)` / `assert.doesNotMatch` 的正反成对断言。

四类断言：

1. **正向** —— 条件成立时该段必须在。
2. **反向** —— 条件不成立时该段必须**不在**。（防「以为切了其实没切」）
3. **契约恒在** —— 遍历全部 fixture，断言 §二 那张表里每一个报数入口在**组装后的请求**里至少出现一次。**这是「一定能触发」的那道保证。**
4. **成对关系** —— 工具被藏时对应说明段也必须不在；说明段在时工具也必须在。把 §二 末尾那条「约定不是机制」变成机制。

## 七、第三步：段落装配重构（逐字节等价）

现在的条件逻辑是**对拼好的大字符串做正则手术**（`tracker_prompt_context.js:312-324`）：

```js
baseGuide = baseGuide.replace(/\n?\[wardrobe \/ outfit\][\s\S]*?\n\[descriptions\]/, '\n[descriptions]');
baseGuide = baseGuide.replace('、psychology', '')...
```

正则或字面量对不上时 `replace` **静默返回原串，不报错** —— 该切的没切，全量照发。谁改了段头文字、谁在 `[wardrobe / outfit]` 和 `[descriptions]` 之间插了一段，这些手术就会悄悄失效。这就是「该触发没触发 / 该切没切」的结构性来源。

改法：把 `TRACKER_VARIABLE_GUIDE_PROMPT` 从一个 join 好的大字符串改成**有序段落表**，每段 `{ id, tier: 'contract'|'band'|'stage', when, text }`：

- 装配 ＝ `filter`，不再有正则。
- `tier: 'contract'` 的段**在代码层面禁止带 `when`**（装配时断言强制），契约层不可能被条件化。
- 段落 id 找不到时**抛错**，而不是悄悄全量输出。

⚠️ **这一步不动任何口径**：同样的文字、同样的顺序、同样的输出。安全性来自第一步的黄金文件 —— **改造前后必须逐字节完全一致**。这是把「一定能触发」从「靠人记得」变成结构性的那一步，也是整个卡最硬的一道闸。

横向坑 #11 正好指向这里：「新表进 config 文件、引擎函数尽量独立文件——别继续往七千行的 `tools.js` 里堆。」段落表同理，不要留在 `tracker_prompt_context.js` 里继续膨胀。

## 八、第四步：工具两件事 —— 先按阶段门控，再去重

**2026-09-04 实测后调整了顺序：门控是大头（4469 字符），去重是小头（约 500）。原先把去重排在前面是估错了。**

### 4a. 按阶段门控（大头）

24 个工具 17783 字符，按「什么时候才有意义」分三组：

| 组 | 个数 | 字符 | 现状 |
|---|---|---|---|
| 今天已有门 | 6 | 5149 | `bsWriteDiary` / `bsUpdatePsychology` / `bsRuptureMembranes` / 衣柜三件 |
| **只有孕育中才有意义** | **7** | **4469** | **今天无条件发** ← 这里 |
| 永远要在 | 11 | 8140 | 不动 |

那 7 个：`bsForceGestation` 1050 / `bsSetGestationLock` 890 / `bsImplantEmbryo` 788 / `bsMaternalFetalInteraction` 630 / `bsAbortion` 591 / `bsNameChild` 290 / `bsChildbirth` 230。

非孕角色一个都不该被调，却每轮都发。逐个的门：

- `bsImplantEmbryo` —— 工具描述自己写着「已进入妊娠阶段后不可再加入」，所以妊娠阶段起就必然无效，可藏。
- `bsNameChild` —— 没有 `children` 就无从命名。
- `bsChildbirth` / `bsAbortion` / `bsMaternalFetalInteraction` —— 无孕无产程时无意义。
- `bsForceGestation` / `bsSetGestationLock` —— 强制令类。⚠️ **不要用「正文里有没有强制令关键词」当门**，那就掉回 §三 那个因果倒置的坑了。保守：这两个不藏，或只按「有没有已注册角色」藏。

扩展的是 `getTrackerToolDefinitions`（`tracker.js:438`）里那个 `hiddenTools` 集合，跟今天四组门同一套机制。这一步比去重安全：藏掉不是「删说明」，是**这个阶段这件事不该发生**，反而降低误调用。既有 `bsRuptureMembranes` 的注释写的就是这个理由（「破水只在产兆前驱与前两个产程有意义；平时挂着只是占用模型的注意力」）。

⚠️ 每加一个门，第二步的**成对关系断言**必须同步：工具藏了，对应说明段也得跟着藏；说明段还在而工具没了，模型会去调一个不存在的工具。

### 4b. 描述去重（小头）

不是「去重」，是**逐句判定唯一真源还是重复**。

**规则：system prompt 侧有同义句的才允许删；没有的一律留。** 参数名、枚举值一律保留（那是 schema 面，模型靠它选工具、填枚举）。

`bsUpdateCharacterStatus` 3178 字符是单个工具里最大的，但里面真重复的只有性欲那四句：

- `libidoClass` 0-5 梯子（对 `tracker_prompt_context.js:254`）
- 「刺激分钟不等于本轮分钟」（对 `:255`）
- 「去没去…一概不要你判断」（对 `:256`）
- `fetalPushback` 轻5中10强20（对 `:227`）

约 400~500 字符。体力三档、`urineSense` 九种、`sweating`、`urineStressEvent`、`vitalitySugar`、`stoolMeal`、`prolongedPregnancy` 全是唯一真源（见 §二），**一个字不能动**。

第二步的契约恒在断言就是这一步的安全网：删过头，那条断言当场红。

## 十三、不改代码就能先省的三个开关

⚠️ **这三个是现成设置，零风险，实测时先试这个再决定要不要开工前五步。**

| 开关 | 默认 | 省 |
|---|---|---|
| `contextSize` | 12 | **未知，可能是最大项** |

| `raceCatalogInPrompt` | true | 关掉 → `[可用种族名录]` 500 |

`contextSize` 是唯一没被算进 §一 那 30250 里的大项，因为它是变量。关键事实：**插件不截断**——`buildRecentMessages`（`state.js:1795`）直接 `text: String(message.mes || '')` 送全文，没有任何长度上限；`trimMainflowSnapshotContent` 名字像截断，实际是空壳 `return String(content || '')`。

所以它的量 ＝ **你一条消息的字符数 × contextSize**：

- 一条 1500 字 → 12 条 18000 字符，**比 system 还大**，这时候 12→6 一次省 9000，比前五步加起来的三倍还多
- 一条 400 字 → 12 条 4800 字符，无所谓，前五步才是主要的

**这个数决定整张卡值不值得做，而它只有实测才知道。** 实测前不要先动代码。
